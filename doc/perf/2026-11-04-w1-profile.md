# innd W1 intake profile, macOS (2026-11-04)

Where innd spends its time while it takes in articles (scenario W1 of the
performance comparison, `doc/perf/2026-11-04-alpha3.md`).  Asked for by
the architect after that comparison showed innd's W1 CPU time is 93%
system time (user 0.87 s, system 12.4 s).

## Summary

- About 85% of the intake is filesystem system calls made by two
  components: the tradspool storage method (about 62%) and the history
  index flush (about 20%).
- Header and body parsing is under 2%.  Work on innd's header handling
  (`HDRCONTENT`, the pointer-and-length steps) is for correctness and
  clarity; it will not move W1 throughput noticeably.
- alpha3 and the 2.8.0 baseline have the same profile, within 1 point
  for every row.  The conversion did not move it.
- The tradspool share was measured on APFS.  It may be much smaller on
  Linux filesystems, so it is being re-measured there before any storage
  work is chosen.

## Method

- W1 on the 40,000-article feed (52,100 group placements, 1.3 groups per
  article), tradspool storage, tradindexed overview, hisv6 history, the
  sample `inn.conf` (`icdsynccount: 10`).
- 3 repetitions per build, alternating, with
  `support/perf/run-compare.sh` and its new `PERF_PROFILE` setting.
- macOS `sample` read innd's stacks every 1 ms for 11 s of each intake
  (about 6,900 samples per run).  Each sample is credited to the function
  at the top of its stack and to the nearest innd functions below it.
- Sampling slowed the intake by about 20% (wall time 15.8–18.9 s against
  12.7–13.2 s unsampled), equally in both builds.  The shares, not the
  times, are the result.
- The 6 runs agree within about 2 points on every row.
- Apple M3 Pro, macOS 27.0.1, APFS on the internal SSD.

## Where the time goes

Average of 3 runs per build, as a share of all samples.

| Component | Call | alpha3 | baseline |
|---|---|---:|---:|
| tradspool | `link` (crosspost hard links) | 33.8% | 33.2% |
| tradspool | `open` (create the article file) | 21.0% | 20.9% |
| tradspool | `writev`, `close` | 7.0% | 6.8% |
| history | `msync` in `dbzsync` | 20.2% | 20.3% |
| history | write and check the history line | 2.5% | 3.0% |
| overview | tradindexed: `msync`, `write`, `pwrite`, locks | 7.3% | 7.3% |
| innd | `ARTparse`, `ARTparsebody` | 1.6% | 1.7% |
| innd | everything else (network, logging, feeds) | about 6% | about 6% |

Call chains:
- tradspool: `ARTstore` → `SMstore` → `tradspool_store`.
- history: `HISwrite` → `hisv6_write` → `hisv6_writeline` → `hisv6_sync`
  → `dbzsync` → `putcore` → `msync` (`lib/dbz.cc:1341`).
- overview: `OVadd` → `tradindexed_add` → `tdx_data_add`.

## Findings

### Tradspool: one file per article, plus a link per extra group

`tradspool_store` (`storage/tradspool/tradspool.cc`) creates a file for
each article and hard-links it into each further group it is posted to.
The feed makes 40,000 files and only about 12,100 links, yet `link` costs
more than all the `open` calls.  Hard links are known to be expensive on
APFS.  ext4 and XFS may not show this, so this share is not acted on until
the Linux run.

CNFS, INN's storage method that writes articles into large preallocated
buffers, makes no per-article files or links.  The Linux run measures W1
under both methods.

### History: dbzsync flushes the whole index

`dbzsync` calls `putcore` (`lib/dbz.cc:1341`), which calls
`msync(tab->core, conf.tsize * tab->reclen, MS_ASYNC)`.  That is the whole
hash table, every `icdsynccount` articles (10 by default).  `MS_ASYNC`
does not wait for the disk, but the kernel still walks the whole mapping,
so each call costs time in proportion to the table's size, not to what
changed.

Two ways to reduce it:
- Flush only the pages written since the last sync: track the lowest and
  highest changed offsets in `dbzstore`.  This keeps the crash safety
  `icdsynccount` gives.  It applies on every platform.
- Raise `icdsynccount`.  This is a configuration change only, but more
  articles can be lost from history in a crash.

The first is recorded as a refactoring candidate (CONVERSION_NOTES.md,
"dbzsync flushes only what changed").

### Header parsing is not the bottleneck

`ARTparse` and `ARTparsebody` take 1.6% between them; the rest of innd's
own code is a few percent more.  The parsing work already planned stays
worth doing for correctness and safety, but not for intake speed.
