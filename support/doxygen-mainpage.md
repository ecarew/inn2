INN++ architecture {#mainpage}
==================

How INN's programs fit together: who receives articles, where they are
kept, and who sends them on.  This is the overview; the program and
library structure is generated by CMake (`CMakeGraphVizOptions.cmake` in
the repository root), and the file, function and class pages below are
generated from the sources.

**Receiving.**  innd is a single process that multiplexes every
connection as a channel (innd/chan.cc).  Peers offer articles with IHAVE
or TAKETHIS (innd/nc.cc); rnews hands batches to innd the same way, and
nnrpd passes on what readers post.  innd parses each article in place in
the channel's buffer (innd/art.cc), checks it against history, files it
with the storage API, writes its overview data (unless overchan does) and
records it in history and the active file.

**Sending on.**  For each site in newsfeeds that wants the article, innd
writes a line to the site's channel (site.cc): a file read later by
nntpsend and innxmit, a pipe to a program such as innfeed, overchan or
controlchan, or an exploder such as buffchan.

**Reading.**  Readers talk to nnrpd, either handed over by innd or started
on its own.  nnrpd reads the stored data through the same libraries, and
gives posted articles to innd.

**Controlling.**  ctlinnd sends commands to innd over a Unix-domain
control channel (innd/cc.cc).  expire and expireover, run daily by
news.daily, remove old articles from history, the spool and overview.

**Libraries.**  libinn (lib/) is the shared utility library: wildmat,
network, configuration, dates and headers.  libinnstorage (storage/)
holds the storage and overview methods behind one API each
(`SMstore`/`SMretrieve`, `OVadd`/`OVopensearch`), and libinnhist
(history/) the history methods behind `HISwrite`/`HISlookup`.
