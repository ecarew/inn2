# innd W1 intake profile, macOS and Linux (2026-11-04)

Where innd spends its time while it takes in articles (scenario W1 of the
performance comparison, `doc/perf/2026-11-04-alpha3.md`).  Asked for by
the architect after that comparison showed innd's W1 CPU time is 93%
system time (user 0.87 s, system 12.4 s).

## Summary

The first part below is the macOS tradspool profile.  The later sections
add Linux, CNFS and timecaf, and revise two of its conclusions:
- Most of the macOS cost is macOS: on Linux the same tradspool intake is
  about 8 times faster, with a twelfth of the system time.
- Parsing is innd's largest user-code cost once storage is cheap.  The
  "header parsing is not the bottleneck" finding holds on macOS with
  tradspool only.

Ranked for CNFS and timecaf sites on Linux (see "What to work on"):
`ARTparsebody`'s body scan first, then `HDRCONTENT`, then the two `msync`
items, which matter mainly on macOS and the BSDs.

### macOS, tradspool

- About 85% of the intake is filesystem system calls made by two
  components: the tradspool storage method (about 62%) and the history
  index flush (about 20%).
- Header and body parsing is under 2% (revised below for Linux and for
  CNFS and timecaf).
- alpha3 and the 2.8.0 baseline have the same profile, within 1 point
  for every row.  The conversion did not move it.
- The tradspool share was measured on APFS; on Linux it is much smaller
  (see "Linux").

## Method

- W1 on the 40,000-article feed (52,100 group placements, 1.3 groups per
  article), tradspool storage, tradindexed overview, hisv6 history, the
  sample `inn.conf` (`icdsynccount: 10`).
- 3 repetitions per build, alternating, with
  `support/perf/run-compare.sh` and its new `PERF_PROFILE` setting.
- macOS `sample` read innd's stacks every 1 ms for 11 s of each intake
  (about 6,900 samples per run).  Each sample is credited to the function
  at the top of its stack and to the nearest innd functions below it.
- Sampling slowed the intake by about 20% (wall time 15.8–18.9 s against
  12.7–13.2 s unsampled), equally in both builds.  The shares, not the
  times, are the result.
- The 6 runs agree within about 2 points on every row.
- Apple M3 Pro, macOS 27.0.1, APFS on the internal SSD.

## Where the time goes

Average of 3 runs per build, as a share of all samples.

| Component | Call | alpha3 | baseline |
|---|---|---:|---:|
| tradspool | `link` (crosspost hard links) | 33.8% | 33.2% |
| tradspool | `open` (create the article file) | 21.0% | 20.9% |
| tradspool | `writev`, `close` | 7.0% | 6.8% |
| history | `msync` in `dbzsync` | 20.2% | 20.3% |
| history | write and check the history line | 2.5% | 3.0% |
| overview | tradindexed: `msync`, `write`, `pwrite`, locks | 7.3% | 7.3% |
| innd | `ARTparse`, `ARTparsebody` | 1.6% | 1.7% |
| innd | everything else (network, logging, feeds) | about 6% | about 6% |

Call chains:
- tradspool: `ARTstore` → `SMstore` → `tradspool_store`.
- history: `HISwrite` → `hisv6_write` → `hisv6_writeline` → `hisv6_sync`
  → `dbzsync` → `putcore` → `msync` (`lib/dbz.cc:1341`).
- overview: `OVadd` → `tradindexed_add` → `tdx_data_add`.

## Findings

### Tradspool: one file per article, plus a link per extra group

`tradspool_store` (`storage/tradspool/tradspool.cc`) creates a file for
each article and hard-links it into each further group it is posted to.
The feed makes 40,000 files and only about 12,100 links, yet `link` costs
more than all the `open` calls.  Hard links are known to be expensive on
APFS.  ext4 and XFS may not show this, so this share is not acted on until
the Linux run.

CNFS, INN's storage method that writes articles into large preallocated
buffers, makes no per-article files or links.  The Linux run measures W1
under both methods.

### History: dbzsync flushes the whole index

`dbzsync` calls `putcore` (`lib/dbz.cc:1341`), which calls
`msync(tab->core, conf.tsize * tab->reclen, MS_ASYNC)`.  That is the whole
hash table, every `icdsynccount` articles (10 by default).  `MS_ASYNC`
does not wait for the disk, but the kernel still walks the whole mapping,
so each call costs time in proportion to the table's size, not to what
changed.

Two ways to reduce it:
- Flush only the pages written since the last sync: track the lowest and
  highest changed offsets in `dbzstore`.  This keeps the crash safety
  `icdsynccount` gives.  It applies on every platform, but see "Linux":
  there `MS_ASYNC` is a no-op, so the gain is mainly on macOS and the BSDs.
- Raise `icdsynccount`.  This is a configuration change only, but more
  articles can be lost from history in a crash.

The first is recorded as a refactoring candidate (CONVERSION_NOTES.md,
"dbzsync flushes only what changed").

### Header parsing on macOS with tradspool

`ARTparse` and `ARTparsebody` take 1.6% between them here, because
tradspool's system calls dwarf everything else.  This does not hold once
storage is cheap: see "CNFS and timecaf".

## Linux

W1 in Docker's Linux VM: Debian trixie, kernel 6.10.14-linuxkit, arm64,
12 CPUs, on ext4 (a Docker volume, not the container's overlay
filesystem).  The current HEAD built `RelWithDebInfo`, the same 40,000
articles, 3 repetitions per method, alternating.  Every run accepted all
40,000.  tradspool has one `storage.conf` entry; CNFS and timecaf have the
typical 8-entry layout (`PERF_LAYOUT=typical`): control, junk, two
binaries entries the feed never matches, three hierarchy entries and a
catch-all, so each article is matched against 5 to 8 entries.

| | tradspool | CNFS | timecaf |
|---|---:|---:|---:|
| Wall time | 1.49–1.69 s | 1.05–1.20 s | 1.30–1.41 s |
| Articles/s | 23,600–26,900 | 33,300–38,000 | 28,500–30,700 |
| innd user CPU | 0.55–0.57 s | 0.55–0.58 s | 0.69–0.72 s |
| innd system CPU | 0.88–1.06 s | 0.46–0.58 s | 0.57–0.64 s |

An earlier Linux run with a single CNFS entry gave 1.08–1.10 s and the same
CPU times: the 8 entries cost nothing measurable.

Findings:
- **tradspool is about 8 times faster on Linux than on macOS** (1.5–1.7 s
  against 12.7–13.2 s), and innd's system time falls from 12.4 s to about
  1 s.  APFS's file creation and hard links, and macOS's `msync`, made up
  most of the macOS profile.
- **CNFS is about 1.45 times tradspool, timecaf about 1.2 times.**
  Without per-article files, innd's system time halves.
- **`msync(MS_ASYNC)` is a no-op on Linux** ("Since Linux 2.6.19, MS_ASYNC
  is in fact a no-op", msync(2)): the kernel tracks dirty pages itself.
  That is why the history and overview flushes that dominate macOS hardly
  show here.
- **User time is about half of innd's CPU on Linux** (a third with
  tradspool), against 7% on macOS.  innd's own code matters here.
- The VM's disk is virtual, and all writes fit in its page cache, as on
  macOS.  Absolute numbers on real hardware will differ; the ratios between
  methods are the robust result.

## CNFS and timecaf

Where the time goes under CNFS and timecaf, from macOS stack samples with
the same typical layout (`PERF_LAYOUT=typical`, 3 repetitions each).  macOS
gives the split of innd's own code; its system-call shares overstate
`msync` (see "Linux").  Shares are of busy samples (idle `select` time left
out); the third repetition is shown, the others agree within about a point.

| Component | CNFS | of which user code | timecaf | of which user code |
|---|---:|---:|---:|---:|
| History flush (`dbzsync` → `msync`) | 31.5% | 0.2% | 27.7% | 0.1% |
| Overview (tradindexed) | 26.2% | 2.8% | 16.3% | 1.9% |
| Network (reading articles, replies) | 14.0% | 3.1% | 7.8% | 1.6% |
| History write and lookup | 9.0% | 5.5% | 5.9% | 3.7% |
| Parsing (`ARTparse`, `ARTparsebody`) | 8.8% | 8.8% | 4.1% | 4.1% |
| Storage method's store | 7.3% | 0.4% | 36.2% | 1.6% |
| `storage.conf` matching (`SMgetsub`, `MatchGroups`) | 0.9% | 0.9% | 0.6% | 0.6% |
| `ARTmakeoverview` | 0.5% | 0.5% | 0.4% | 0.4% |
| `ARTstore` (iovec list, header copy) | 0.2% | 0.2% | 0.1% | 0.1% |

macOS throughput, sampled: CNFS 6,800–7,200 articles/s, timecaf
4,400–4,500.

Findings:
- **Parsing is innd's largest user-code cost:** about 37% of its user
  time under CNFS.  About two-thirds of it is `ARTparsebody`, the body
  scan (article terminator, line counts, bare LF and NUL checks), which
  goes byte by byte (`innd/art.cc`).  Header parsing is the other third:
  on Linux, roughly 5–6% of innd's CPU under CNFS.
- **`storage.conf` matching is under 1%** even with 8 entries.
  `MatchGroups` allocates, copies and `strtok`s Newsgroups for each entry,
  but that is not worth changing for speed.
- **The storage methods never parse headers.**  CNFS and timecaf write
  `ARTstore`'s iovec list with one `xwritev`; the per-article header work
  is all in innd, before `SMstore`.
- **Overview's cost is mostly `msync`:** `tdx_data_add`
  (`storage/tradindexed/tdx-group.cc`) flushes the group's index entry
  with `inn_msync_page` up to three times per article.
- **timecaf uses about 25% more user time than CNFS** on Linux, in its
  CAF file handling.

## What to work on

For CNFS and timecaf sites on Linux, the deployment that matters most:
1. **`ARTparsebody`: a faster body scan**, with `memchr` for `\r` and
   `\n` instead of testing each byte (CONVERSION_NOTES.md, "ARTparsebody
   body scan").  innd's largest user-code cost; self-contained and easy
   to test.
2. **`HDRCONTENT`**: finish the views and remove the `HDR` macros.  A
   modest speed gain; mostly correctness and clarity.
3. **The two `msync` items**: `dbzsync` (CONVERSION_NOTES.md, "dbzsync
   flushes only what changed") and tradindexed's per-article entry flush
   (CONVERSION_NOTES.md, "tradindexed flushes the group entry per
   article").  Large on macOS and the BSDs; small on Linux, where
   `MS_ASYNC` is a no-op.
4. `MatchGroups` and `ARTHANDLE` views: cleanup only.

Not measured: a Linux profile of innd's user code (`perf` in a privileged
container) would confirm the user-code split above on Linux.
